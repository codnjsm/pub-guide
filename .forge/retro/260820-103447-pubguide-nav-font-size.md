# 2026-08-20 — 좌측 네비게이션 메뉴 글자 크기 반응형 조정

## Plan vs actual
- What went as planned: 2개 슬라이스 착지. `App.vue` 전역 스타일로 `.v-list-item--nav .v-list-item-title`을 덮어썼고(`@layer` 밖이라 `!important` 불필요), Vuetify가 걸어둔 `line-height: 1rem` + `overflow: hidden` 때문에 줄높이도 함께 지정했다. 조정 라운드마다 빌드/린트 재실행, 전부 통과.
- Divergences:
  - **값이 4라운드 왕복했다** — 계획서 18/16/14 → 16/14/12 → 15/14/12 → 14/14/12 → 최종 **15/15/13**.
  - **구조가 3구간 → 2구간으로 바뀌었다** — PC·태블릿을 합치면서 `max-width: 959.98px` 미디어쿼리가 통째로 사라졌다. 계획서의 "Vuetify 브레이크포인트 3구간" 전제 자체가 없어진 셈인데, 결과적으로 규칙은 단순해졌다.
  - 최종 모바일 13px는 Vuetify 기본값과 같아, "기본값을 키운다"는 의도가 사실상 600px 이상에만 적용된다. 코드 주석을 실제 동작에 맞게 고쳤다.

## Learnings

### 눈으로 정해지는 값은 계획서에 확정값처럼 박지 않는다 + fg-visual 제안을 놓치지 않는다 (승급하지 않음)
폰트 크기·여백처럼 **화면에서 봐야만 정해지는 값**을 계획서에 숫자로 확정해 적으면, 실행 직후 바로 낡는다. 이번엔 계획서의 표가 첫 라운드에 무효가 됐다.

두 가지를 같이 한다:
1. 계획서에는 **"요청값으로 시작해 화면 보고 조정"**임을 명시한다. 숫자는 시작점이지 완료조건이 아니다. (완료조건은 "세 구간이 실제로 다르게 보이고 잘리지 않는다"처럼 값에 독립적으로 쓴다 — 이번엔 이건 잘 돼 있었다.)
2. **`fg-visual` 제안 여부를 그릴링에서 판단한다.** 이번 작업은 "18은 너무 크다 → 15 → 합치자 → 15/13"으로 네 번 왕복했는데 전부 말로 주고받았다. fg-ask는 "보여주는 게 말하는 것보다 명확한 질문이 처음 나오는 순간 제안하라"고 정해두는데, 나는 브레이크포인트만 묻고 크기는 요청값을 그대로 받아 적어 **제안 자체를 놓쳤다.**

**이 계열은 이번이 세 번째다** — 검색 패널 회고("캡쳐 기준으로 맞춘 뒤 눈으로 보며 미세 조정은 정상 흐름"), 전체메뉴 회고("치수가 중요한 요소는 실제 CSS를 콕 집어 요청"), 그리고 이번. 세 번 모두 "시각적 판단이 필요한 값을 텍스트로 왕복했다"는 같은 뿌리다. **다음에 또 나오면 회고 로그를 넘어 별도 작업 가이드 문서를 만들 근거로 삼는다.** 지금은 README(코드 규칙 문서)에 넣을 성격이 아니라 회고에만 남긴다.
